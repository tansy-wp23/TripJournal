# TripJournal User App UI/UX Redesign

## Goal

Redesign the authenticated and guest-facing TripJournal experience as a coherent, modern travel-journal app while preserving all existing product behavior, Supabase data flows, validation, map behavior, and user data.

The redesign targets Android phones first. Web must remain usable and free of overflow, but it does not receive a separate desktop information architecture in this phase.

## Confirmed scope

Included:

- Guest and authentication screens
- Home and trip library
- Trip detail, Entries, Map, photos, wellness, and trip summary
- Entry creation, editing, viewing, and location picking
- Community discovery and public trip detail
- Profile, profile editing, Settings, and Recently Deleted
- Shared loading, empty, error, confirmation, and feedback states
- Complete Light, Dark, and System theme support

Excluded:

- Admin screens
- Changes to database schemas, repositories, business rules, or Supabase data
- Localization; interface copy remains English
- A new logo, launcher icon, or splash artwork
- A dedicated tablet or desktop navigation model

## Visual direction

The selected direction is **Sky & Aurora**: bright sky blue, atmospheric cyan-to-indigo gradients, and a restrained adventure-orange accent. It should feel energetic and travel-oriented without turning every surface into a gradient.

Photography remains the strongest visual content. Gradients appear in active-trip heroes, selected highlights, empty-state illustrations, and small ambient accents. Regular forms, lists, maps, dialogs, and long-form journal content use quiet solid surfaces.

### Light palette

- Background: pale sky `#F0F9FF`
- Surface: white `#FFFFFF`
- Raised/secondary surface: ice blue `#E8F5FA`
- Primary: accessible sky blue `#0369A1`
- Secondary: cyan `#0E7490`
- Accent/action: deep adventure orange `#C2410C`
- Main text: deep ocean `#0C4A6E`
- Secondary text: slate `#475569`
- Border: `#BAE6FD`
- Error: `#B91C1C`

### Dark palette

- Background: deep ocean `#071521`
- Surface: `#0D2233`
- Raised/secondary surface: `#143247`
- Primary: luminous sky `#38BDF8`
- Secondary: cyan `#67E8F9`
- Accent/action: warm orange `#FB923C`
- Main text: `#E6F6FF`
- Secondary text: `#A9C4D4`
- Border: `#1C4057`
- Error: `#FCA5A5`

Dark mode is independently designed, not generated by simple inversion. Maps and photographs retain their own imagery while controls and overlays use dark theme surfaces with readable contrast.

## Type, shape, spacing, and motion

- Keep the Android system font for dependable rendering and no new font download.
- Use weight, size, and spacing for hierarchy; do not use handwriting fonts for body copy or forms.
- Use an 8-point spacing rhythm with 4-point adjustments for compact details.
- Primary cards use 16–24 px visual corner radii; small controls use 12–16 px; destructive and data-heavy surfaces remain quieter.
- Touch targets are at least 44×44 logical pixels with at least 8 px separation where practical.
- Standard transitions last roughly 180–300 ms and communicate navigation, selection, expansion, or successful completion.
- Reduced-motion environments receive the final state without decorative movement.

## Theme and component architecture

Create a centralized theme layer rather than placing colors and dimensions in individual screens:

- `AppTheme`: Light and Dark `ThemeData`
- `AppColors`/theme extension: aurora gradient and semantic travel-specific colors not covered by `ColorScheme`
- `AppSpacing`, `AppRadii`, and `AppDurations`: shared layout and motion tokens
- Shared components for screen headers, hero cards, section headers, trip cards, filter/search controls, empty/error states, primary actions, and settings sections

All components obtain colors and text styles through `Theme.of(context)` or theme extensions. Screen code must not depend on a static Light or Dark palette.

## Navigation and information architecture

Authenticated users receive a stable root app shell with three destinations:

1. **Trips** — dashboard, active trip, and trip library
2. **Community** — public discovery and destination search
3. **Profile** — profile overview, Settings, Recently Deleted, and account actions

A prominent orange create action is separate from the destination navigation:

- On the Trips root, it creates a Trip.
- Within a Trip, the primary action adds an Entry.
- It does not open an ambiguous menu and is not presented as a fourth destination.

Trip detail keeps local `Entries | Map` tabs. Wellness, photos, trip summary, editing, and publishing remain secondary Trip destinations. Root-tab switching preserves each destination's scroll position and active filters. Android system back and the visible back affordance follow the same navigation history.

Guest users retain Community-first browsing with a clear sign-in action. They do not see authenticated Profile or create actions.

## Screen design

### Trips home

- Compact personalized header with existing profile avatar
- Active-trip hero using the aurora treatment, day progress, destination, and a direct journal prompt
- Small wellness/entry indicators with text labels, not color alone
- Search and sort/filter controls grouped into one predictable toolbar
- Photo-led trip cards with destination, dates/status, entry count, and clear tap affordance
- Contextual create button with an accessible label

### Trip detail, Entries, and Map

- Photo-led trip header that remains readable with or without a cover photo
- Compact trip facts and summary actions below the hero
- Persistent local `Entries | Map` segmented control
- Entry timeline grouped by travel day, keeping immutable creation order within a day
- Search and filters remain independent and visibly active
- Map day chips remain horizontally usable, and map overlays use theme-aware high-contrast surfaces
- Route arrows, marker previews, clustering, fallbacks, and route disclaimers preserve their current behavior

### Entry and Trip forms

- Break long forms into clearly titled sections on one scrollable page
- Keep visible labels and helper/error text close to their fields
- Place the primary save action consistently; show disabled/loading/success states
- Preserve all current validation, unsaved-change handling, photo behavior, location search, pin dragging, and current-location actions

### Community

- Photo-first discovery feed with destination and trip context
- Search is visible or one tap away and active query state is obvious
- Public-trip detail shares visual components with private Trip detail while hiding owner-only controls

### Profile and Settings

- Profile becomes the owner of Settings and Recently Deleted navigation
- Separate identity, travel preferences, app preferences, and account safety into clear card groups
- Destructive account actions remain visually separated and require existing confirmations
- Theme selection previews System, Light, and Dark clearly

### Guest and authentication

- Preserve existing flows and Google sign-in behavior
- Reuse the current brand artwork
- Use aurora accents, concise benefits, and an obvious primary sign-in action
- Authentication errors remain readable and actionable

## State, data, and error behavior

The redesign does not change controllers, repositories, models, Supabase calls, or persistence formats. Existing providers remain the source of truth. UI components receive already-available view state and emit the same existing callbacks.

Every data-driven surface defines loading, empty, populated, filtered-empty, recoverable-error, and unavailable states. Loading feedback reserves stable layout space where practical. Errors explain what failed and expose Retry only when the existing controller can retry safely. Snackbars remain for brief confirmations; field errors stay beside the field; destructive choices use dialogs or confirmation screens.

## Accessibility and responsive behavior

- Normal text contrast is at least 4.5:1 in both themes.
- Focus, selected, error, loading, and disabled states are distinguishable without color alone.
- Icons have tooltips or semantic labels when text is absent.
- Text scaling must not clip primary actions or navigation labels.
- Layouts are checked at common Android phone widths, narrow 320 px width, landscape phone constraints, and Web widths.
- `LayoutBuilder` or existing responsive patterns replace assumptions about a fixed 375 px screen.

## Implementation sequence

1. Theme tokens and shared foundations
2. Root app shell and navigation state
3. Trips home and reusable trip cards
4. Trip detail, Entries, Map overlays, and related secondary screens
5. Trip and Entry forms
6. Community and public trip screens
7. Profile, Settings, Recently Deleted, guest, and authentication screens
8. Cross-screen accessibility, responsive, Light/Dark, and regression polish

Each phase keeps the app runnable and uses the existing test suite as its behavioral contract.

## Verification

- Add focused widget tests before each changed behavior or component contract.
- Preserve existing widget keys where they are part of tests or automation.
- Run targeted tests during each phase.
- Run `flutter analyze --no-pub` and the full Flutter test suite before integration.
- Manually verify Android Light, Dark, and System modes on the configured emulator.
- Manually verify Trips, Entry creation/editing, Map day filters/routes, Community, Profile, Settings, logout, and guest sign-in.
- Do not create or modify real cloud data except in explicitly user-approved test trips.
